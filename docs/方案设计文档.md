# AI 闯关学习微信小程序方案设计文档

## 1. 文档信息

- 项目名称：AI 闯关学习微信小程序
- 文档类型：技术方案设计文档
- 需求来源：[PRD.md](PRD.md)
- 首版目标：跑通核心业务闭环
- 首版技术路线：Taro + React + TypeScript + Python（FastAPI/Flask）+ 国内 OpenAI-compatible AI 服务

## 2. 项目背景与核心目标

本项目希望解决“学习过程枯燥、反馈慢、互动弱、复盘难”的问题。用户只需要输入一个想学的主题或粘贴一段知识内容，小程序就能通过 AI 自动生成闯关题，让用户逐题答题、即时获得讲解，并在完成后生成复盘报告。

首版不是做完整学习平台，也不是做复杂题库系统，而是验证一个最短可用闭环：

```text
用户输入内容 -> AI 生成题目 -> 用户答题 -> AI 生成分析报告
```

首版必须优先保证这条链路稳定、可演示、可迭代。登录注册、云端历史记录、支付、排行榜、多人 PK、RAG 知识库、文档/网页/视频解析都不作为第一阶段依赖。

## 3. MVP 边界与分阶段路线

### 3.1 V1 核心范围

V1 只做以下能力：

1. 用户输入学习主题或粘贴一段文本。
2. 调用 Python API 生成 5 道单选题。
3. 小程序端逐题展示题目与选项。
4. 用户选择答案后立即看到正误、正确答案和知识讲解。
5. 全部答完后调用 Python API 生成复盘报告。
6. 复盘页展示得分、正确率、核心总结、错题回顾、薄弱点和学习建议。
7. 完成后将题目快照、答题结果和报告保存到 PostgreSQL。
8. 用户可通过历史记录页查看已完成学习记录。
9. 当前答题中的学习会话仍保存在前端状态和小程序本地缓存中。

### 3.2 V1 明确不做

- 不做强制微信登录和显式注册流程。
- 不做手机号、密码、个人资料编辑等完整账户体系。
- 不保存未完成答题进度到云端。
- 不做微信支付、VIP、额度系统。
- 不做文档上传、网页抓取、视频转写。
- 不做多人 PK、排行榜、数字人、语音读题。
- 不做 RAG 私有知识库。
- 不做复杂题型，例如多选题、填空题、主观题评分。

### 3.3 分阶段路线

| 阶段 | 目标 | 主要交付 |
| --- | --- | --- |
| Step 1 | 先跑通后端生成题库接口 | Python API、LangChain 调用、5 道题结构化输出、接口测试 |
| Step 2 | 再做前端闯关页面 | 使用生成题库接口返回的数据完成逐题答题、正误反馈、讲解展示 |
| Step 3 | 再做报告生成接口 | 根据答题结果生成复盘报告，失败时返回可识别错误 |
| Step 4 | 最后接入首页形成闭环 | 首页输入接入生成题库接口，串起首页、闯关页、报告页 |
| Step 5 | 稳定性与体验补强 | loading、错误重试、本地缓存、内容安全、mock/fake model 测试 |
| Step 6 | 数据持久化与历史记录 | 微信静默身份、PostgreSQL、完成后保存、历史列表和详情 |

这个顺序刻意把首页放到最后，不是因为首页不重要，而是因为首页只是入口；真正的技术风险在 AI 题目结构化生成、闯关页消费题目数据、报告接口引用真实答题结果。先把这三段跑稳，再接首页，能更快形成可靠闭环。

## 4. 小程序技术选型对比

小程序生态迭代快，方案需要兼顾开发效率、平台能力、后续维护和扩展空间。结合本项目首版目标，重点对比微信原生、Taro React、uni-app Vue。

### 4.1 微信原生小程序

优势：

- 与微信平台能力贴合度最高。
- 官方工具链完整，调试路径直接。
- 运行时模型最接近微信小程序本身。
- 适合只做微信端、页面少、业务逻辑简单的项目。
- 原生已支持 TypeScript 开发，开发者工具内置编译能力。

劣势：

- 组件化和状态管理体验弱于 React/Vue 工程体系。
- 复杂交互状态较多时，代码组织容易分散。
- 后续如果要扩展 H5、其他小程序平台或 App，需要重新适配。
- 生态组件、工程规范、测试体系需要自行搭建更多约定。

适合场景：

- 明确只做微信端。
- 页面数量少，交互简单。
- 团队更熟悉原生小程序。

本项目不作为主方案的原因：

- 本项目虽然 V1 页面不多，但后续会扩展题库、报告、历史、分享、垂直场景，状态与组件复用会越来越重要。
- 已确认前端倾向 Taro React，使用 React 组织复杂交互更合适。

### 4.2 Taro + React + TypeScript

优势：

- 使用 React 组件化和 TypeScript 类型系统，适合维护复杂交互状态。
- 支持微信小程序，也为后续 H5、多端小程序预留空间。
- 业务逻辑、组件、hooks、类型定义可按现代前端工程方式组织。
- 对独立开发者友好，工程化能力比原生更完整。
- 可以把答题状态机、AI 返回结构校验、报告展示等逻辑拆成可测试模块。

劣势：

- 比微信原生多一层框架编译和适配。
- 部分微信平台细节仍需回到原生小程序文档确认。
- 不适合过度依赖平台特殊组件或极致性能调优的首屏页面。

适合场景：

- 希望用 React/TypeScript 组织业务。
- 首版做微信端，但后续可能扩展到 H5 或其他端。
- 需要较好的组件复用、状态抽象和测试能力。

本项目选择原因：

- 核心业务包含“输入、生成、答题、反馈、报告”的多状态流程，React 更适合维护状态流转。
- Taro 能发布微信小程序，同时保留后续多端扩展空间。
- TypeScript 可以明确 AI 结构化输出、题目、会话和报告的数据契约，降低 AI 返回异常导致的运行时风险。

### 4.3 uni-app + Vue

优势：

- 基于 Vue 生态，多端能力强。
- uni-app 生态成熟，插件和模板丰富。
- 对熟悉 Vue 的开发者上手快。
- 支持微信、支付宝、百度、抖音、App、H5 等多端。

劣势：

- 当前技术偏好已选 Taro React。
- 对 React 技术栈团队而言，会引入额外学习成本。
- 本项目核心不是“最大化跨端发布”，而是先验证微信端 AI 学习闭环。

适合场景：

- 团队主要使用 Vue。
- 项目从一开始就明确要多端同步发布。
- 希望使用 uni-app 生态插件快速拼装业务。

本项目不作为主方案的原因：

- 当前已确认选择 Taro React。
- 本项目 V1 的核心难点不是跨端 UI，而是 AI 输出结构化、答题流程和报告生成稳定性。

### 4.4 选型结论

首版采用：

```text
Taro + React + TypeScript + 微信小程序
```

后端采用：

```text
Python（FastAPI/Flask）- AI 生态最好，调用大模型最方便
```

部署方式：

```text
MVP 推荐：CloudBase HTTP 云函数 + Flask
后续复杂服务推荐：CloudBase 云托管 + FastAPI/Flask
```

AI 服务采用：

```text
国内 OpenAI-compatible 接口，优先兼容 DeepSeek / 通义千问等供应商
```

该组合的核心判断：

- 小程序端只做交互与展示，不暴露 AI Key。
- Python API 服务作为 AI 代理层，负责鉴权隔离、Prompt 拼装、结构化校验、错误重试。
- V1 不引入数据库依赖，减少登录、权限、数据模型复杂度。
- 通过 TypeScript 接口约束 AI 输入输出，避免“模型返回什么前端就展示什么”的脆弱设计。
- 后端使用 Python 是为了利用更成熟的 AI 生态；后续扩展 RAG、文档解析、向量检索、PDF 处理、NLP 清洗时，不需要再迁移技术栈。
- CloudBase 不是业务框架，而是微信生态内的部署方式。业务代码仍按 Python Web API 方式组织。

### 4.5 CloudBase 云函数是什么

CloudBase 云函数可以理解为微信/腾讯云提供的 Serverless 后端托管能力：开发者上传一段后端代码，平台负责运行、扩缩容、日志和基础运维。它适合小程序项目隐藏密钥、处理服务端逻辑、连接云数据库或调用第三方 API。

它和 Python（FastAPI/Flask）的关系是：

```text
Python（FastAPI/Flask）= 你怎么写后端服务
CloudBase 云函数 / 云托管 = 你把后端服务部署在哪里
```

如果使用普通 CloudBase 云函数，前端通常通过 `wx.cloud.callFunction` 调用，形态更像“函数入口”。如果使用 CloudBase HTTP 云函数或云托管，则可以把后端写成 Flask/FastAPI 这种标准 Web API，前端通过 `wx.request` 调用接口。

本项目更符合你图里的表达方式：**Python（FastAPI/Flask）作为后端主体**。部署上首版优先用 CloudBase HTTP 云函数 + Flask，因为它轻、免运维、适合两个 API；如果后续要做 RAG、长任务、文件解析、向量库、更多路由和后台能力，再升级为 CloudBase 云托管 + FastAPI。

### 5.1 总体架构

```text
微信用户

  v
Taro React 小程序
  - 输入页
  - 答题页
  - 复盘页
  - 历史记录页
  - 历史详情页
  - 本地会话状态
  |
  | wx.request
  v
Python（FastAPI/Flask）API 服务
  - POST /api/auth/wechat
  - POST /api/generate-quiz
  - POST /api/generate-report
  - POST /api/history
  - GET /api/history
  - GET /api/history/{id}
  - LangChain AI 编排层
  - 输出结构校验
  - JWT 会话校验
  - 错误处理
  |

  v

  - users

  |
```

### 5.2 前后端职责边界

小程序端负责：

- 收集用户输入。
- 展示生成状态。
- 渲染题目和选项。
- 维护当前答题进度。
- 本地判断用户选择是否正确。
- 收集本轮答题结果。
- 展示 AI 生成的复盘报告。
- 保存当前会话到本地缓存，避免刷新丢失。
- 使用微信静默登录换取后端 token。
- 在报告完成后保存学习历史。
- 展示历史列表和历史详情。

Python API 服务负责：

- 隐藏 AI API Key。
- 拼装 Prompt。
- 调用 AI 服务。
- 解析 AI 返回内容。
- 校验题目结构和报告结构。
- 根据题目和答案重新计算分数、正确率和错题。
- 对异常输出进行一次修复或重试。
- 通过微信 code2session 或开发环境 fallback 建立用户身份。
- 保存和查询用户自己的学习历史。
- 返回前端可直接渲染的结构化 JSON。

Python 后端依赖建议：

```text
Flask/FastAPI    Python Web API 框架
LangChain       后端 AI 编排框架，统一 Prompt、模型调用、结构化输出和后续 RAG/Agent 扩展
pydantic        数据结构校验
langchain-openai 适配 OpenAI-compatible Chat Model
SQLAlchemy      数据库 ORM
psycopg         PostgreSQL 驱动
PyJWT           本项目访问 token 签发与校验
httpx           备用底层 HTTP 客户端或非 LangChain 能力补充
tenacity        请求重试
python-dotenv   本地开发读取环境变量
pytest          Python API 核心逻辑测试
```

当前实现采用 FastAPI。原因是接口数量已经从单纯 AI 生成扩展到认证、历史记录和报告保存，FastAPI 的类型约束、依赖注入和测试体验更适合继续演进。

后续后端开发统一使用 LangChain 作为 AI 编排框架。V1 只使用 LangChain 的轻量能力：Chat Model 适配、Prompt Template、结构化输出和 Pydantic 校验；暂不使用复杂 Agent、多工具调用、LangGraph 工作流或 RAG。等进入文档解析、知识库、向量检索阶段，再扩展 LangChain Retriever、VectorStore、Tool、Agent 等能力。

AI 服务负责：

- 根据输入生成题目。
- 根据答题结果生成复盘报告。
- 不直接面向小程序端暴露。

### 5.3 数据库接入策略

早期 MVP 可以只用前端本地缓存验证核心学习体验；在核心闭环稳定后，历史记录已经成为产品继续使用的基础能力，因此当前接入 PostgreSQL，但仍控制范围：

- 只保存完成后的学习记录，不保存未完成答题进度。
- 用户身份采用微信静默登录，不增加显式注册登录页面。
- 数据表先保持两张核心表：`users` 和 `learning_records`。
- `learning_records` 保存题目、答案和报告 JSON 快照，避免后续 AI 输出变化影响历史回看。
- 后端查询历史时必须按当前用户过滤，避免跨用户读取。

这样既补齐云端历史，又不把范围扩大到完整账户体系、学习画像或错题本。

## 6. 核心业务流程设计

### 6.0 MVP 实施流程

MVP 按接口优先、闭环后置的顺序实现：

```text
1. 先把后端 POST /api/generate-quiz 生成题库接口跑通
2. 再做前端闯关页面，直接消费生成题库接口的数据
3. 再做 POST /api/generate-report 报告生成接口
4. 最后把首页接入，形成端到端闭环
```

每一步的验收标准：

- Step 1：直接调用 `POST /api/generate-quiz`，输入一个主题，可以稳定返回 5 道结构合法的单选题。
- Step 2：闯关页可以加载一组题目，完成逐题答题、锁定答案、展示正误和讲解。
- Step 3：直接调用 `POST /api/generate-report`，传入题目和答题结果，可以返回结构合法的复盘报告。
- Step 4：首页输入内容后，能自动进入生成题库、闯关答题、报告生成的完整流程。

开发期间可以先用接口调试工具或本地脚本验证后端接口，不必等首页完成后再测试 AI 生成能力。

### 6.1 学习输入到生成题目

```text
用户进入首页
  -> 输入主题或粘贴文本
  -> 前端做基础校验
  -> 请求 POST /api/generate-quiz
  -> Python API 调用 AI 生成 5 道题
  -> Python API 校验结构
  -> 前端创建 QuizSession
  -> 跳转答题页
```

关键规则：

- 输入为空不能提交。
- 输入去除前后空格后少于 2 个中文字符或少于 4 个英文字符时提示用户补充。
- 输入长度 V1 建议限制在 5000 字以内。
- 题目固定 5 道。
- 每道题固定 4 个选项，至少保证 3 个有效选项。
- 每道题只能有一个正确答案。

### 6.2 用户答题

```text
展示第 N 题
  -> 用户选择选项
  -> 前端锁定答案
  -> 前端判断正误
  -> 展示正确答案和讲解
  -> 用户点击下一题
  -> 如果还有题，进入下一题
  -> 如果已完成，进入报告生成
```

关键规则：

- 用户作答前不展示正确答案。
- 用户作答后不能修改本题答案。
- 答题结果只在前端会话中记录，V1 不上传数据库。
- 每题记录 `questionId`、`selectedOptionId`、`isCorrect`、`answeredAt`。

### 6.3 生成复盘报告

```text
完成最后一题
  -> 前端汇总 sessionResult
  -> 请求 POST /api/generate-report
  -> Python API 调用 AI 生成报告
  -> Python API 校验报告结构
  -> 前端展示复盘页
  -> 本地缓存本次会话和报告
```

关键规则：

- 报告生成失败时，前端使用本地模板兜底展示基础报告。
- 基础报告至少包含正确率、错题列表、题目讲解聚合。
- AI 报告作为增强体验，不应成为展示结果的唯一来源。

## 7. 前端页面与模块设计

### 7.1 页面结构

V1 当前包含 5 个核心页面：

```text
pages/index/index          首页 / 输入页
pages/quiz/index           答题页
pages/report/index         复盘报告页
pages/history/index        历史记录页
pages/history-detail/index 历史详情页
```

后续阶段再增加：

```text
pages/share/index          分享落地页
```

### 7.2 首页 / 输入页

核心元素：

- 产品标题和一句说明。
- 多行文本输入框。
- 示例主题快捷按钮。
- “生成闯关”主按钮。
- “查看历史记录”入口。
- 加载状态和错误提示。

交互逻辑：

- 用户可以输入主题或长文本。
- 点击生成前做本地校验。
- 生成中禁用按钮，避免重复提交。
- 生成成功后创建会话并跳转答题页。
- 生成失败时根据后端错误码展示更具体的提示。
- 点击历史记录入口跳转历史列表。

建议示例主题：

- AI Agent 是什么
- 机器学习入门
- 面试中的闭包问题
- 基金定投基础
- 英语现在完成时

### 7.3 答题页

核心元素：

- 当前进度，例如 `第 2 / 5 题`。
- 题目知识点标签。
- 题干。
- 选项列表。
- 作答后的正误反馈。
- 正确答案。
- 知识讲解。
- 下一题 / 生成报告按钮。

状态设计：

```text
unanswered: 未作答
answered_correct: 已作答且正确
answered_wrong: 已作答且错误
completed: 全部完成
```

交互规则：

- 未作答时只展示题干和选项。
- 点击选项后立即进入已作答状态。
- 已作答后选项不可再次点击。
- 答对选项显示正确态。
- 答错时用户选项显示错误态，正确选项显示正确态。
- 最后一题按钮文案为“生成复盘报告”。

### 7.4 复盘报告页

核心元素：

- 学习主题。
- 得分和正确率。
- 核心知识总结。
- 错题回顾。
- 薄弱点分析。
- 后续学习建议。
- 历史保存失败提示。
- “再学一次”按钮。
- “返回首页”按钮。

报告生成成功后，前端调用历史记录接口保存本次学习结果。V1 可暂不做真实微信分享，但页面结构应为后续 `onShareAppMessage` 预留标题、路径和摘要。

### 7.5 历史记录页

核心元素：

- 历史记录数量。
- 按完成时间倒序展示的学习记录列表。
- 每条记录展示主题、分数、正确率、完成时间。
- 加载态、空态、失败态和重新读取按钮。

交互逻辑：

- 进入页面时先通过静默微信身份确保后端 token 可用。
- 历史接口失败时展示可重试错误。
- 点击记录进入历史详情页。

### 7.6 历史详情页

核心元素：

- 学习主题和完成时间。
- 分数、正确率和报告摘要。
- 题目快照、用户答案、正确答案和讲解。

交互逻辑：

- 通过记录 id 请求后端详情。
- 只展示已保存快照，不重新调用 AI。
- 记录不存在或不属于当前用户时展示错误态。

### 7.7 前端模块划分

建议模块：

```text
src/types/learning.ts          核心类型
src/services/api.ts            Python API 调用封装
src/services/auth.ts           微信静默身份与 token 缓存
src/services/history.ts        历史记录接口封装
src/services/session.ts        本地会话读写
src/hooks/useQuizSession.ts    答题状态管理
src/utils/quiz.ts              正误判断、分数计算
src/utils/validators.ts        输入校验
src/components/OptionCard      选项组件
src/components/LoadingState    加载态
src/components/ErrorState      错误态
```

实现原则：

- 页面只负责组合 UI 和调用 hooks。
- 答题状态流转放到 `useQuizSession`。
- 分数计算和错题提取放到纯函数，便于测试。
- API 调用统一经过 `services/api.ts`，不要在页面里直接散落调用。
- 认证和历史记录调用独立封装，页面不直接拼接 token 或请求头。

## 8. Python API 与 AI 服务设计

### 8.1 API 列表

当前 V1 后端 API：

```text
POST /api/auth/wechat
POST /api/generate-quiz
POST /api/generate-report
POST /api/history
GET  /api/history
GET  /api/history/{id}
```

MVP 可由一个 FastAPI 应用承载这些路由；后续迁移到 CloudBase 云托管或其他 Python 服务时，路由和服务层代码可以基本保留。

推荐后端模块：

```text
backend/app/main.py
backend/app/auth.py
backend/app/database.py
backend/app/history.py
backend/app/llm.py
backend/app/models.py
backend/app/prompts.py
backend/app/schemas.py
backend/app/wechat.py
```

### 8.2 POST /api/generate-quiz

职责：

- 接收学习输入。
- 做服务端基础校验。
- 拼装题目生成 Prompt。
- 通过 LangChain 调用 AI。
- 使用 LangChain 结构化输出或 Pydantic 解析结果。
- 校验题目结构。
- 返回标准题目列表。

前端请求契约：

```ts
interface GenerateQuizRequest {
  input: LearningInput
}
```

前端响应契约：

```ts
interface GenerateQuizResponse {
  ok: boolean
  data?: AiGenerationResult
  error?: AppError
}
```

错误类型：

```text
INVALID_INPUT        输入为空、过短或过长
AI_REQUEST_FAILED    AI 服务调用失败
AI_OUTPUT_INVALID    AI 返回结构不可用
CONTENT_BLOCKED      内容安全拦截
UNKNOWN_ERROR        未知错误
```

### 8.3 POST /api/generate-report

职责：

- 接收本轮题目和答题结果。
- 计算正确率基础数据。
- 拼装报告生成 Prompt。
- 通过 LangChain 调用 AI。
- 校验报告结构。
- 返回标准复盘报告。

前端请求契约：

```ts
interface GenerateReportRequest {
  session: QuizSession
}
```

前端响应契约：

```ts
interface GenerateReportResponse {
  ok: boolean
  data?: ReviewReport
  error?: AppError
}
```

兜底策略：

- 如果 AI 报告生成失败，Python API 可以返回错误。
- 前端收到错误后使用本地模板报告，不阻断用户查看结果。

### 8.4 LangChain AI 编排层

AI 服务采用 OpenAI-compatible 接口，但不能把业务代码写死到某一家供应商。Python 后端统一通过 LangChain 编排模型调用、Prompt 和结构化输出，业务层不直接调用模型 SDK。

建议抽象：

```python
from typing import TypeVar
from pydantic import BaseModel

T = TypeVar("T", bound=BaseModel)

class LangChainClient:
    def generate_structured(
        self,
        system_prompt: str,
        user_prompt: str,
        output_schema: type[T],
    ) -> T:
        """Use LangChain chat model + structured output to return a validated Pydantic object."""
        ...
```

环境变量建议：

```text
OPENAI_BASE_URL=https://api.deepseek.com
OPENAI_API_KEY=xxx
OPENAI_MODEL=deepseek-v4-flash
OPENAI_TIMEOUT_SECONDS=60
OPENAI_MAX_RETRIES=2
DATABASE_URL=postgresql+psycopg://brain_rush:brain_rush@localhost:5432/brain_rush
AUTH_TOKEN_SECRET=change-me-in-production
WECHAT_APPID=xxx
WECHAT_SECRET=xxx
```

供应商切换规则：

- DeepSeek、通义千问或其他国内兼容接口只需要替换 `OPENAI_BASE_URL`、`OPENAI_API_KEY`、`OPENAI_MODEL`。
- `LangChainClient` 内部负责初始化兼容 OpenAI 协议的 Chat Model。
- 业务层不直接感知供应商名称，也不直接拼接 HTTP 请求。
- 若某供应商不稳定，优先在 LangChain 编排层做降级，而不是改页面逻辑。

Python API 建议分层：

```text
main.py       FastAPI 路由入口
llm.py        LangChain 模型调用与结构化输出封装
prompts.py    Prompt 模板
schemas.py    Pydantic 请求/响应模型
history.py    历史记录保存与查询
auth.py       JWT 签发与当前用户依赖
wechat.py     微信 code2session 与开发环境 fallback
database.py   SQLAlchemy engine/session/Base
models.py     users、learning_records 数据表模型
```

## 9. 数据结构设计

V1 同时需要前端会话结构和后端持久化结构。前端答题过程仍以 `QuizSession` 为核心；完成后由后端保存学习记录快照。

### 9.1 LearningInput

```ts
interface LearningInput {
  type: 'topic' | 'text'
  content: string
  createdAt: string
}
```

规则：

- `type` 由前端根据输入长度和用户入口判断。
- V1 可以不要求用户手动选择类型。
- `content` 为清洗后的文本，去掉首尾空格。

### 9.2 QuizQuestion

```ts
interface QuizQuestion {
  id: string
  knowledgePoint: string
  stem: string
  options: QuizOption[]
  correctOptionId: string
  explanation: string
}

interface QuizOption {
  id: string
  text: string
}
```

规则：

- `id` 可由 Python API 生成，格式建议 `q1`、`q2`。
- 选项 `id` 建议固定为 `A`、`B`、`C`、`D`。
- `correctOptionId` 必须命中某个选项。

### 9.3 QuizSession

```ts
interface QuizSession {
  id: string
  input: LearningInput
  questions: QuizQuestion[]
  answers: UserAnswer[]
  status: 'answering' | 'completed' | 'report_ready'
  currentIndex: number
  startedAt: string
  completedAt?: string
  report?: ReviewReport
}
```

规则：

- V1 的 `id` 可由前端生成。
- `answers.length` 不能超过 `questions.length`。
- `currentIndex` 由前端状态管理，不依赖服务端。

### 9.4 UserAnswer

```ts
interface UserAnswer {
  questionId: string
  selectedOptionId: string
  correctOptionId: string
  isCorrect: boolean
  answeredAt: string
}
```

规则：

- `isCorrect` 由前端根据 `selectedOptionId === correctOptionId` 计算。
- 提交报告时把完整 answers 传给 Python API。

### 9.5 ReviewReport

```ts
interface ReviewReport {
  summary: string
  score: number
  correctRate: number
  keyPoints: string[]
  weakPoints: string[]
  wrongQuestionReview: WrongQuestionReview[]
  nextSteps: string[]
}

interface WrongQuestionReview {
  questionId: string
  reason: string
  suggestion: string
}
```

规则：

- `score` 为 0-100。
- `correctRate` 为 0-1。
- `wrongQuestionReview` 只包含错题。
- 没有错题时，`weakPoints` 可以为空，`nextSteps` 给出进阶建议。

### 9.6 AiGenerationResult

```ts
interface AiGenerationResult {
  title: string
  inputSummary: string
  questions: QuizQuestion[]
}
```

规则：

- `questions.length` V1 必须等于 5。
- `title` 用于答题页和报告页展示。
- `inputSummary` 用于复盘页解释本轮学习范围。

## 10. Prompt 与结构化输出设计

### 10.1 题目生成 Prompt 原则

Prompt 目标：

- 从用户输入中提取适合学习的核心知识点。
- 生成 5 道单选题。
- 每题覆盖一个明确知识点。
- 选项要有迷惑性，但不能故意误导。
- 解析要解释为什么正确、为什么常见错误不对。

系统提示词建议：

```text
你是一个专业的学习题目设计助手。
你需要把用户输入的学习主题或文本转化为适合微信小程序闯关学习的单选题。
请只输出合法 JSON，不要输出 Markdown，不要输出额外解释。
题目必须准确、清晰、适合初学者到中等水平用户。
如果用户输入不足以生成题目，请返回空 questions 并说明原因。
```

用户提示词应包含：

```text
学习内容：
{{content}}

请生成 5 道单选题。
每道题包含：
- knowledgePoint
- stem
- options: A/B/C/D 四个选项
- correctOptionId
- explanation

返回 JSON 结构必须符合：
{
  "title": "本轮学习标题",
  "inputSummary": "学习内容摘要",
  "questions": [...]
}
```

### 10.2 题目输出校验

Python API 必须校验：

- LangChain 返回值能通过 Pydantic schema 校验。
- `questions` 是数组。
- `questions.length === 5`。
- 每题 `stem` 非空。
- 每题 `options` 至少 3 个，推荐 4 个。
- 每题 `correctOptionId` 命中某个选项。
- 每题 `explanation` 非空。
- 每题 `knowledgePoint` 非空。

如果校验失败：

1. 尝试通过 LangChain 结构化输出重新生成一次。
2. 仍失败则返回 `AI_OUTPUT_INVALID`。
3. 前端展示可重试错误。

### 10.3 报告生成 Prompt 原则

Prompt 目标：

- 基于真实答题结果生成复盘。
- 不虚构用户没有答过的题。
- 错题分析要对应具体错题。
- 建议要短、明确、可执行。

系统提示词建议：

```text
你是一个专业的学习复盘教练。
你需要根据用户本轮答题结果生成复盘报告。
请只输出合法 JSON，不要输出 Markdown，不要输出额外解释。
报告要鼓励用户继续学习，但不要夸大结论。
如果用户全部答对，请给出进阶学习建议。
```

返回 JSON 结构：

```json
{
  "summary": "本轮学习总结",
  "keyPoints": ["知识点1", "知识点2"],
  "weakPoints": ["薄弱点1"],
  "wrongQuestionReview": [
    {
      "questionId": "q2",
      "reason": "错误原因",
      "suggestion": "复习建议"
    }
  ],
  "nextSteps": ["下一步建议1", "下一步建议2"]
}
```

`score` 和 `correctRate` 建议由程序计算，不交给 AI 决定，避免模型输出与真实答题结果不一致。

## 11. 错误处理与降级策略

### 11.1 前端错误

| 场景 | 处理 |
| --- | --- |
| 输入为空 | 提示“请输入想学习的主题或内容” |
| 输入过短 | 提示“内容太短，请补充更多信息” |
| 生成中重复点击 | 禁用按钮 |
| 题目生成失败 | 根据后端错误码展示差异化提示和重试按钮 |
| 答题页无会话 | 返回首页并提示重新生成 |
| 报告生成失败 | 展示错误提示和重新生成按钮 |
| 历史读取失败 | 展示失败态和重新读取按钮 |

### 11.2 Python API 错误

| 错误码 | 说明 | 前端展示 |
| --- | --- | --- |
| invalid_input | 输入不合法 | 请补充更完整的学习内容 |
| ai_auth_error | AI 服务配置或鉴权异常 | AI 服务配置暂不可用，请检查后端配置 |
| ai_rate_limited | 上游限流 | AI 请求有点拥挤，请稍后再试 |
| ai_timeout | 模型调用超时 | AI 思考超时，请换个主题或稍后重试 |
| ai_connection_error | 上游连接异常 | 暂时连不上 AI 服务，请稍后重试 |
| ai_invalid_response | AI 输出结构异常 | 生成结果异常，请重试 |
| ai_upstream_error | 上游未知异常 | AI 服务暂时开小差了，请稍后重试 |
| unauthorized | 未登录或 token 失效 | 请重新进入页面后再试 |

### 11.3 报告失败处理

当 `generateReport` 失败时，前端保留当前答题数据，展示可重试错误态，不写入历史记录。页面仍可根据本地数据展示加载态统计：

- 正确题数 / 总题数。
- 正确率。
- 错题列表。
- 每道错题的原始讲解。

历史记录保存只发生在报告生成成功之后，避免保存半成品报告。

## 12. 内容安全与合规

### 12.1 V1 最小安全策略

V1 至少需要做：

- 前端限制输入长度。
- Python API 校验输入内容是否为空、过短、过长。
- 对明显违法、色情、暴力、仇恨、诈骗等内容做关键词级拦截或调用内容安全能力。
- AI 输出展示前做结构校验。
- 分享内容不包含用户隐私和完整答题明细。

### 12.2 高风险领域提示

对于医疗、法律、金融投资等主题，报告和讲解中应避免绝对化建议。可在 Prompt 中加入约束：

```text
如果内容涉及医疗、法律、金融投资等高风险领域，请只做通识学习解释，不要给出具体诊断、法律结论或投资建议。
```

### 12.3 API Key 安全

- AI API Key 只能保存在 Python 后端环境变量中。
- 小程序端不得出现 API Key。
- 后端日志不得打印完整 API Key。
- 错误日志可记录模型名、错误码、请求耗时，不记录用户完整敏感输入。

## 13. 开发流程与里程碑

### 13.1 Step 1：后端生成题库接口

目标：

- 建立 Python（Flask/FastAPI）API 服务目录。
- 使用 LangChain 接入 OpenAI-compatible 模型。
- 实现 `POST /api/generate-quiz`。
- 用 Pydantic 校验生成题目结构。

交付：

- 本地可启动 Python API。
- 输入主题或文本后返回 5 道单选题。
- 每道题包含题干、4 个选项、正确答案、知识点和讲解。
- AI 返回异常时能返回 `AI_OUTPUT_INVALID`。

验收：

- 用接口调试工具或本地脚本调用 `POST /api/generate-quiz` 成功。
- 使用 fake/mock chat model 时测试稳定通过。
- 使用真实模型时至少 5 个常见主题能生成合法题目。

### 13.2 Step 2：前端闯关页面

目标：

- 答题页。
- 逐题答题状态管理。
- 正误反馈和讲解展示。
- 可以消费 `POST /api/generate-quiz` 返回的数据。

交付：

- 独立闯关页可加载一组题目。
- 用户逐题选择答案。
- 每题即时反馈。
- 最后一题完成后产出本轮 `QuizSession` / `sessionResult`。

验收：

- 不依赖首页也能进入闯关页调试。
- 使用接口真实返回数据时页面可完整答完 5 题。
- 已答题不能重复修改。

### 13.3 Step 3：报告生成接口

目标：

- 实现 `POST /api/generate-report`。
- 根据真实题目和用户答题结果生成复盘报告。
- 报告失败时给前端明确错误，前端可兜底。

交付：

- 后端报告接口。
- 报告结构校验。
- 错题回顾、薄弱点和下一步建议。

验收：

- 用 Step 2 产生的 `sessionResult` 调用报告接口成功。
- 报告中的错题 ID 只来自真实错题。
- 报告生成失败时前端展示本地兜底报告。

### 13.4 Step 4：首页接入形成闭环

目标：

- 实现首页输入。
- 首页调用 `POST /api/generate-quiz`。
- 生成成功后进入闯关页。
- 闯关完成后调用报告接口进入复盘页。

交付：

- 首页 / 输入页。
- 首页到闯关页的数据传递。
- 闯关页到报告页的数据传递。
- 端到端完整流程。

验收：

- 用户从首页输入“机器学习入门”，可完成生成题目、答题、生成报告。
- 不登录、不建用户表，也能完整完成一次学习。
- API Key 不出现在小程序端。

### 13.5 Step 5：稳定性与体验

目标：

- 完善 loading、empty、error 状态。
- 增加本地缓存。
- 增加结构校验和错误重试。
- 增加基础内容安全。

交付：

- 生成失败可重试。
- 刷新或退出后可恢复当前会话。
- AI 输出结构异常不会导致页面崩溃。

验收：

- mock 异常输出时前端展示错误而不是白屏。
- 答题中断后重新进入可恢复。

### 13.6 Step 6：小范围测试

目标：

- 用真实主题测试 Prompt 质量。
- 收集题目是否准确、是否有趣、讲解是否清楚。
- 调整 Prompt 和输出校验策略。

测试主题建议：

- AI Agent 是什么
- JavaScript 闭包
- 基金定投基础
- 英语现在完成时
- 产品经理面试题

验收：

- 题目相关性基本可接受。
- 5 道题全部结构稳定。
- 复盘报告能准确引用错题。

### 13.7 已完成：数据持久化

目标：

- 引入 PostgreSQL。
- 保存完成后的历史学习记录。
- 通过微信静默身份区分用户。
- 提供历史列表和历史详情。

当前边界：

- 只保存报告生成成功后的完整记录。
- 不保存未完成答题进度。
- 不做显式注册登录、用户资料编辑和账号绑定。

## 14. 测试方案

### 14.1 测试原则

- 先测核心行为，再测实现细节。
- AI 结果不可稳定断言，测试中使用 mock。
- 结构校验、状态流转、兜底策略必须可测试。
- 页面视觉细节不作为 V1 阻塞项，核心流程不可阻塞。

### 14.2 前端测试重点

- 输入为空时不能提交。
- 正常输入能进入生成中状态。
- 生成成功后创建会话。
- 答题状态从未答到已答正确/错误。
- 已答题不能重复修改。
- 最后一题完成后进入报告流程。
- 报告失败时展示可重试错误态。
- 报告成功后保存历史记录。
- 历史列表可以读取当前用户的记录。
- 历史详情展示题目、答案和报告快照。

### 14.3 Python API 测试重点

- `generateQuiz` 能处理正常输入。
- `generateQuiz` 能拒绝空输入。
- AI 返回非 JSON 时返回 `AI_OUTPUT_INVALID`。
- AI 返回题目数量不足时返回 `AI_OUTPUT_INVALID` 或重试。
- `generateReport` 使用真实答题结果生成报告。
- 报告中的错题 ID 必须来自用户真实错题。
- Python 后端核心逻辑使用 `pytest` 测试，不依赖真实 AI 服务。
- Pydantic schema 校验覆盖缺字段、字段类型错误、正确答案不在选项中等情况。
- LangChain 调用层使用 fake/mock chat model 测试，避免单元测试依赖真实模型。
- 测试重点是 Prompt 输入、结构化输出 schema、错误映射和重试策略，不断言真实模型文案。

### 14.4 验收用例

1. 输入“机器学习入门”，生成 5 道单选题。
2. 输入空内容，按钮不可提交或提示补充内容。
3. AI 返回结构异常，页面展示“生成结果异常，请重试”。
4. 用户答对一题，页面显示正确状态、正确答案和讲解。
5. 用户答错一题，页面显示错误状态、正确答案和讲解。
6. 用户完成 5 道题，页面展示正确率和复盘报告。
7. 用户无需显式登录，也能通过微信静默身份保存历史。
8. 报告 AI 调用失败，页面展示可重试错误态，且不会保存半成品历史。
9. 报告成功后，历史列表出现该记录。
10. 历史详情展示已保存的题目快照、用户答案和报告内容。

## 16. 关键风险与应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| AI 生成题目质量不稳定 | 用户不信任产品 | 结构校验、Prompt 迭代、题目反馈 |
| AI 输出格式不稳定 | 前端渲染失败 | Python API 强校验、失败重试、mock 兜底 |
| 首版范围过大 | 无法快速上线 | 严格只做核心闭环 |
| API Key 泄露 | 安全风险 | 只放 Python 后端环境变量 |
| AI 成本不可控 | 运营压力 | 固定 5 题、限制输入长度、限制重试次数 |
| 小程序合规问题 | 无法审核上线 | 内容安全、隐私最小化、分享内容审查 |
| 用户不知道输入什么 | 激活率低 | 示例主题、输入提示、热门主题 |
| 历史记录越权读取 | 用户数据泄露 | 后端按当前用户过滤历史记录，详情接口校验记录归属 |
| 数据库连接或迁移失败 | 历史记录不可用 | 提供初始化脚本、本地 `.env.example`、历史页错误态和重试入口 |

- `docs` 放后续补充文档，例如接口文档、测试记录、上线清单。

## 18. 开发优先级清单

严格按以下顺序推进：

1. 初始化 Python 后端服务目录。
2. 实现 LangChain Client、Prompt、Pydantic Schema。
3. 实现 `POST /api/generate-quiz`，先用 fake/mock chat model 跑通。
4. 接入真实 AI，让生成题库接口稳定返回 5 道题。
5. 初始化 Taro React TypeScript 小程序项目。
6. 实现闯关页，直接消费生成题库接口返回的数据。
7. 实现 `POST /api/generate-report`，先用 fake/mock chat model 跑通。
8. 接入真实 AI，让报告接口能基于答题结果生成复盘。
9. 实现复盘页，接入报告接口和本地兜底报告。
10. 最后实现首页输入，并接入生成题库接口。
11. 串起首页 -> 生成题库 -> 闯关页 -> 报告接口 -> 复盘页。
12. 增加 loading、错误重试、结构异常处理和本地缓存。
13. 小范围真实主题测试并调整 Prompt。
14. 再决定是否接入云数据库和历史记录。

这个顺序的核心原则是：先把 AI 后端接口打穿，再做消费接口的闯关页；先验证报告接口能引用真实答题结果，再接首页入口。首页放最后，避免一开始花时间做入口和样式，却还不知道后端生成结构是否稳定。
